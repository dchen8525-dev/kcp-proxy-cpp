# Protocol

## Architecture

The client exposes a local SOCKS5 listener. Each accepted TCP connection gets its own KCP session over UDP
to the server. The server maps UDP source endpoint to one `KCPSession`, then opens one outbound TCP
connection for the SOCKS5 CONNECT target.

## KCP Handshake

CPP clients may send `KCP_PROXY_HELLO_V1` inside encrypted KCP data before SOCKS5 data. The server replies
with `KCP_PROXY_HELLO_ACK_V1`. The C++ client reports the KCP session as connected only after this
authenticated reply arrives.

As a compatibility mode, the server also accepts a first payload that is directly a SOCKS5 CONNECT request
(no HELLO required). The server accepts either first payload:

- `KCP_PROXY_HELLO_V1`: send `KCP_PROXY_HELLO_ACK_V1`, then wait for SOCKS5.
- SOCKS5 CONNECT bytes: treat the first valid encrypted KCP/SOCKS5 packet as the compatibility handshake
  and continue to TCP connect.

C++ client handshake timeout is `3s`. Wrong key, missing server, or blocked UDP produces handshake
failure/timeout instead of a fake connected state.

## Crypto

- Cipher: AES-128-GCM.
- Key derivation: HKDF-SHA256.
- HKDF salt: `kcp-proxy-hkdf-salt-v1` concatenated with a 16-byte cryptographically
  random **per-session salt** generated by the client for every session. The same
  salt is carried in cleartext at the front of every encrypted datagram (see Wire
  format) so the server can derive the identical per-session key from the first
  packet. This guarantees every session uses an independent AEAD key, so
  counter/nonce values can never collide across sessions (AES-GCM nonce reuse
  would otherwise be catastrophic). 16 bytes keeps the honest collision
  probability negligible and makes it infeasible to collide with a live session
  by guessing; the server additionally refuses to create a session whose salt is
  already claimed by a live session.
- HKDF info:
  - client to server: `kcp-proxy/c2s/v1`
  - server to client: `kcp-proxy/s2c/v1`
- Wire format: `session_salt(16) || nonce(12) || ciphertext || tag(16)`.
  - `session_salt` is the per-session random salt described above (cleartext, not
    secret). It is present on **every** datagram, not just the first.
- Nonce layout: 8-byte big-endian packet counter, 1-byte direction, 3 zero bytes.
  The counter's **starting value is derived from the salt** (first 6 bytes,
  big-endian), so the nonce sequence is unique per session even if two sessions
  were ever forced to share a key.
- Direction byte: client `0x01`, server `0x02`.
- Maximum counter: `2^48 - 1`; encryption throws after that and the session must be recreated.
- Minimum CLI key length: 16 characters.

`Crypto` instances are not thread-safe. They own reusable OpenSSL EVP contexts plus mutable counter and
replay-window state. Production code confines each instance to a single KCP session and serializes calls
through that session's Asio strand.

Normal receivers use a 2048-packet sliding replay window (increased from 64 to absorb UDP packet
reordering in high-throughput scenarios such as large downloads). The server authenticates the first
encrypted UDP packet before allocating KCP session state, but it uses the same per-session `Crypto`
object that will own the session. That means the first accepted packet seeds the replay window before its
decrypted bytes are injected into KCP; replaying that packet to the live session is rejected. There is
intentionally no global replay window across all clients because a client may create a fresh UDP socket
per connection, starting its counter at 0.

**Per-session key isolation (interop-critical).** Every session derives a *unique* AEAD key from
`PSK || session_salt`. The server learns `session_salt` from the first packet and then verifies, with a
constant-time compare, that every subsequent packet of that session carries the **same** salt. A packet
with a different salt is rejected as a cross-session injection attempt. This fixes the previous behavior
where an empty user salt caused every session to derive the *identical* key, so any session's first
packet could be decrypted by any other session's `Crypto`.

**Android CPP_REMOTE must implement the same scheme** or it will not interoperate with this server:
- Generate a 16-byte random `session_salt` per session and prepend it to every encrypted datagram.
- Derive the per-session AES key via HKDF-SHA256 with the same app salt + session salt and direction info.
- Derive the nonce counter's starting value from the first 6 bytes of the salt (big-endian) and begin each session's counter there.
- Carry `session_salt` on every packet (the server re-derives from the first packet and checks it on the rest).
Failing to prepend/verify the salt will cause the server to reject traffic (salt mismatch / decrypt failure).

## Application-layer keepalive

To prevent a live but idle tunnel (e.g. an idle SSH session) from being reaped by the
`KCP_TIMEOUT_SEC` (60s) idle sweep, each side sends an application-layer heartbeat when it has been
silent for longer than `KCP_KEEPALIVE_SEC` (30s). The heartbeat payload is the sentinel
`KCP_PROXY_KEEPALIVE_V1` ("KCP_PROXY_KEEPALIVE_V1"), sent as its own KCP message. The receiver recognizes
this exact payload in `try_fulfill_read` and drops it instead of forwarding it into the downstream TCP
socket.

**Android CPP_REMOTE must recognize and drop `KCP_PROXY_KEEPALIVE_V1`** as well; otherwise it would be
forwarded into the tunnel as garbage data.

## SOCKS5

Supported:

- `CONNECT`
- `ATYP IPv4`
- `ATYP IPv6`
- `ATYP DOMAIN`
- Requests split across multiple KCP reads
- Extra bytes after the CONNECT request; these are forwarded as initial TCP payload after the outbound
  connection succeeds

Unsupported:

- `UDP ASSOCIATE`
- `BIND`

Unsupported commands return SOCKS5 command-not-supported. UDP traffic such as QUIC/HTTP3 and UDP DNS is
not proxied.

On CONNECT success, `BND.ADDR` and `BND.PORT` are taken from the outbound TCP socket local endpoint. If
unavailable, the reply uses `0.0.0.0:0`; it does not echo the target address.

## KCP Settings

- `conv = 1`
- `nodelay = 1`
- `interval = 10ms`
- `fast resend = 5`
- `nc = 1`
- send window `256`
- receive window `512`
- MTU `1400`
- update interval `10ms`
- session timeout `60s`

Server startup logs the same values as:

```text
KCP config conv=1 mtu=1400 nodelay=1 interval=10 resend=5 nc=1 sndWnd=256 rcvWnd=512 timeout=60s
```

## Failure Stages

Logs use these stable stage names where applicable: `AUTH_FAILED`, `DECRYPT_FAILED`, `REPLAY_DETECTED`,
`KCP_INPUT_FAILED`, `KCP_TIMEOUT`, `SOCKS5_PARSE_FAILED`, `SOCKS5_UNSUPPORTED_COMMAND`,
`DNS_RESOLVE_FAILED`, `TCP_CONNECT_FAILED`, `TCP_READ_FAILED`, `TCP_WRITE_FAILED`, `UDP_SEND_FAILED`,
and `SESSION_TIMEOUT`.
